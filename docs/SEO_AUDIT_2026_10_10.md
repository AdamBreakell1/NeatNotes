# RecallStride SEO and Lighthouse audit

Audit date: 10 October 2026. Canonical public site: https://recallstride.com/.

The existing site already passed Lighthouse's limited SEO checklist. The useful improvements were discovery, accurate search descriptions, initial rendering, canonical routing and share previews. The audit did not add keyword pages without useful content, invent reviews or imply endorsement by OCR.

## Search intent and content

Public searches for OCR A-Level Computer Science revision, OCR H446 flashcards and pseudocode practice showed subject-specific revision pages and working coding resources. These searches establish relevant wording, not keyword volumes or predicted traffic. The official [OCR H446 specification](https://www.ocr.org.uk/Images/170844-specification-accredited-a-level-gce-computer-science-h446.pdf) identifies Computer systems and Algorithms and programming as the two examined components.

## Changes implemented

1. **Initial public HTML:** the landing page is visible without JavaScript. It no longer waits for the account/session request or a launch overlay before appearing. A JavaScript-disabled visitor can read the product information and all topic previews.
2. **Loading and layout:** removed the artificial overlay delay and deferred the ordered application scripts. The public footer no longer jumps from the empty page to the bottom when the landing becomes visible.
3. **Titles and descriptions:** home metadata names OCR A-Level Computer Science, H446 and the real pseudocode interpreter. Topic pages have distinct, subject-specific titles and snippets.
4. **Canonical identity:** the home declares `https://recallstride.com/`; topic pages declare their individual canonical URLs. `/index.html` redirects permanently to `/`, preserving account-related query parameters.
5. **Discoverable navigation:** public section navigation uses normal links. The landing page links to all 24 released topic previews, grouped by examined component. Each topic links to neighbouring previews and the complete directory.
6. **Useful topic content:** existing server-rendered previews retain genuine questions from their topic pack, explain how to practise the specific topic, state free/Pro access accurately and preserve the OCR independence and academic-review disclosures.
7. **Structured identity:** WebSite and WebApplication microdata describe the site and free offering; topic previews use LearningResource microdata. No ratings, endorsements, social handles or availability claims were invented. Microdata avoids relaxing the site's Content Security Policy for inline scripts.
8. **Social previews:** Open Graph and Twitter large-card metadata use the exact-brand 1200 × 630 PNG, with image dimensions and descriptive alternative text. The image is in the explicitly public static asset allowlist.
9. **Index control:** API responses and password-reset, verification and billing-return documents have `X-Robots-Tag: noindex, nofollow`. Sensitive action documents have `private, no-store`. Unknown SPA paths return HTTP 404 instead of an indexable 200 duplicate. Authentication remains the access control; robots directives are not treated as a privacy mechanism.
10. **Sitemap and robots:** the sitemap contains the canonical home and the 24 released topic previews. It contains no account routes or hash navigation states. The robots file identifies the canonical sitemap and excludes API/migration crawling.
11. **Published asset size:** esbuild minifies published JavaScript/CSS copies while preserving source files, global APIs and script ordering. Current uncompressed reductions are approximately 23% for app.js, 18% for styles.css and 14% for student-layout.css. esbuild is a pinned direct development dependency.
12. **Anonymous session probe:** the public bootstrap requests the optional session mode, which returns a normal empty session for a signed-out visitor. Authenticated API access retains its original 401 contract. This removes an expected but noisy browser console error.

## Search Console and ongoing work

Google confirmed ownership of the **domain property `recallstride.com`** in [Google Search Console](https://search.google.com/search-console) for the owner's `recallstride@gmail.com` account. Its generated DNS TXT record is installed in Cloudflare. The canonical sitemap was submitted and the submission dialog succeeded, but the latest report still showed **Couldn't fetch**, **Type Unknown**, a last-read date of **10/10/26** and zero discovered pages. Successful sitemap retrieval and completed indexing have not yet been confirmed by Google.

At **21:09 BST on 10 October 2026**, Google's actual URL Inspection live test for `https://recallstride.com/` succeeded with **URL is available to Google** and **Page can be indexed**. This confirms that Google's live inspection service fetched the homepage successfully. The subsequent Request indexing action also succeeded with **Indexing requested** and **URL added to priority crawl queue**. An accepted request is not confirmation that Google has indexed the page. Screenshots are saved at `test-results/launch/google-live-test-passed.png` and `test-results/launch/google-indexing-requested.png`.

The [official property instructions](https://support.google.com/webmasters/answer/34592?hl=en) require the bare domain, without `https://`, a path or `www`. This property includes both apex and www, all protocols and future subdomains. Domain properties require DNS verification; neither a guessed verification token nor a meta tag can verify this property. Keep Google's actual TXT record after verification because ownership is periodically rechecked. Cloudflare DNS access and the owner's Google account are sufficient; no tracking script or Google Analytics installation is needed. See [ownership verification](https://support.google.com/webmasters/answer/9008080?hl=en) and the [Sitemaps report](https://support.google.com/webmasters/answer/7451001?hl=en).

Independent production HTTP checks returned direct 200 responses for the sitemap using normal and Googlebot user agents. Both responses were valid XML with the correct namespace, 25 distinct canonical HTTPS URLs and `application/xml; charset=utf-8`, without a redirect, challenge or `noindex` header. The live robots file permits public crawling and names the exact canonical sitemap; a sample topic is also directly reachable and indexable. IPv4 and IPv6 resolve to Cloudflare. These checks found no application-side sitemap fetch blocker. The successful Google homepage live test supplies actual Google retrieval evidence for the homepage; it does not resolve the separate sitemap report.

The [Sitemaps report guidance](https://support.google.com/webmasters/answer/7451001?hl=en) explains that Unknown can mean a sitemap has not yet been processed; Couldn't fetch still means Google could not retrieve it. Review the sitemap's detailed error and its next provider read. Google retries failed retrievals for several days. Do not describe the current sitemap report or the accepted homepage indexing request as completed indexing, or assume that a new domain alone explains the sitemap failure.

Google decides when to crawl, index and rank a new domain. Do not equate a 100 Lighthouse SEO score with indexing, ranking or marketing readiness. Once Search Console has real data, use its queries, impressions, clicks and coverage to decide which existing topic previews need stronger original explanations. Keep public summaries aligned with the actual course content and product behaviour; do not add fabricated exam predictions, keyword volumes, backlinks, ratings or testimonials.
