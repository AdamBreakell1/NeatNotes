2. Confirm the active zone is `recallstride.com` in account `7656ff3b3eaa33f5eb0e17d1b026f7f0`. Save its non-secret `{ "id": "<32-character-zone-id>", "name": "recallstride.com", "status": "active" }` record privately. Do not fabricate an active record for an unowned name.
3. Run `node scripts/cloudflare-domain.mjs --zone-file /absolute/path/verified-zone.json`. This idempotently prepares apex and www Custom Domain routes, canonical BASE_URL/CORS and Worker-first redirects. It preserves the Worker name, SQLite database binding, migrations and provider-secret preservation. It changes local configuration only.
4. Commit and push the prepared configuration to main. The deployment preflight allows the reviewed transition from the existing Workers origin to the configured RecallStride.com origin and subsequently enforces that canonical origin. Cloudflare creates the Custom Domain DNS records and certificates. If the existing deployment token cannot attach the domain, attach the two Custom Domains through the owner's Cloudflare dashboard or existing Wrangler session; do not replace the database or silently grant unrelated access.
5. Confirm HTTPS on `https://recallstride.com`, www's 308 redirect preserving path/query, and exact release/persistent storage from `/api/health`. Set the GitHub production environment URL to the new origin for the dashboard link. The five application destinations and all APIs remain served by the same Worker and database.

The www and former Workers hostname redirect GET/HEAD traffic to the apex only after the custom origin is configured. Existing verification and reset URLs preserve their query strings. Add and verify the new canonical Stripe webhook endpoint before retiring any old provider endpoint; never treat a redirect as webhook delivery evidence. Checkout, billing-portal returns, email links, robots/sitemap and topic canonicals use BASE_URL. Source: [Cloudflare Worker Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/). Custom Domains require an active zone owned by the account; both hostnames must be configured explicitly.

## Current database recovery

Production uses the existing SQLite Durable Object namespace `a5e9557c19f54431bec4e9ba81337209`, class `RecallStrideDatabase`, and named object `recallstride-production`. Never change these identities for an ordinary deployment. Cloudflare maintains point-in-time history of the object's SQL and key-value data for the previous 30 days. This protects current Cloudflare activity; the historical Render migration snapshot is not a backup of new Cloudflare activity.

Source: [Cloudflare SQLite storage and native recovery API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). Native PITR is unavailable in local development, so native restore validation requires an isolated remote object. Restoring a database is an incident action that requires explicit owner authorization for the chosen time and affected production database.

### Operator procedure

1. Record the incident time, desired recovery point and the exact deployed application revision. Put the existing application in maintenance by setting its operational `MIGRATION_MODE` to `true` in Cloudflare. This freezes public application writes and background maintenance. Preserve provider secrets and the namespace. Do not commit temporary maintenance or recovery credentials to GitHub.
2. Before restoration, preserve the current deletion-request/erasure journal and any outstanding deletion requests outside the database being restored. Record which requests have already been completed. If this cannot be established, keep the service closed; reopening a restored copy could resurrect erased accounts. Separately preserve the incident notes and latest billing reconciliation state. Do not copy customer records into test fixtures or public evidence.
3. Enable operational `RECOVERY_MODE=true` on the existing application. Deploy the temporary `backend/cloudflare/recovery-wrangler.jsonc` Worker using the existing Cloudflare authorization. It binds the existing class by script name and exposes metadata only; the public application has no recovery RPC route. Create a cryptographically random operator secret in a 0600 local file, store it in the temporary Worker's `RECOVERY_SECRET` using Wrangler secret input, and retain neither value in shell history nor logs.
4. Run the recovery CLI against that temporary Worker's HTTPS origin, using `--token-file` and a new private `--output` path for every call. First use `--command status`. Verify the object's ID, native recovery, database size and maintenance status against the expected production namespace/name. Save this current bookmark before choosing an older point.
5. Resolve the chosen UTC time with `--command bookmark --object-id <recorded-id> --timestamp <ISO-UTC-time>`. A time must be within the retained window and after the migration successfully completed. The CLI and database refuse mismatched object IDs. Review the selected timestamp and operational consequences before continuing.
6. Use `--command prepare --object-id <recorded-id> --bookmark <chosen-bookmark> --confirm-restore-object <same-id> --output /private/path/undo.json`. Restoration requires both recovery mode and maintenance plus this exact confirmation. The response records the special undo bookmark privately. **Preparation schedules restoration on the next object restart, including an unexpected restart; save the result immediately and keep maintenance enabled.** The earlier current bookmark is a second recovery reference if the prepare response is lost.
7. After verifying the saved undo record exists outside the object, run `--command restart --object-id <recorded-id> --confirm-restore-object <same-id>` with a separate output path. Re-check status. If the selected restore is wrong, use the saved undo bookmark through the same prepare/restart process while maintenance stays enabled.
8. Verify schema/foreign-key consistency, current application compatibility and the intended recovered accounts/notes/progress through controlled owner checks. Reapply all deletion requests occurring after the restore point, including deletion of their recovered account-owned data, before any restored data is used. Reconcile subscriptions against current Stripe state and reprocess relevant provider events idempotently: an old database must not grant obsolete Pro access or lose later cancellation/payment facts.
9. Disable RECOVERY_MODE, delete the temporary operator Worker and its secret, then disable maintenance once recovery, erasures and billing reconciliation are verified. The helper `node scripts/cloudflare-operator.mjs recallstride-recovery` deletes only the temporary recovery Worker using existing authorization and refuses the production Worker name. Confirm the exact live revision and persistent health. Record the incident/recovery evidence privately, with customer records excluded from the public report.

CLI form (every output must be a new path, and its directory must already exist):

```text
node scripts/cloudflare-recovery.mjs --url https://recallstride-recovery.breakellsystems.workers.dev --token-file /private/path/operator.token --command status --output /private/path/current-bookmark.json
```

The recovery CLI refuses unrecognised remote origins, redirects, broadly readable token files, absent object confirmation and overwritten output files. It does not export customer records. Do not leave RECOVERY_MODE or the temporary Worker enabled between incidents.

### Recovery validation evidence

`node scripts/test-cloudflare-recovery.mjs --remote` creates a distinctly named remote Worker and new SQLite namespace. The fixture uses the actual RecallStride schema with one synthetic verified account/password hash, Pro entitlement, Unicode note and binary record. It saves a native bookmark, damages only those synthetic records, restores them and compares their hashes and foreign keys, then uses Cloudflare's returned undo bookmark to recover the intervening synthetic changes. Cleanup explicitly deletes the fixture class/namespace before deleting its Worker and secret. The recorded results live in `docs/validation/cloudflare-recovery-rehearsal-2026-10-10.json`.

This verifies the implemented native recovery path in an isolated remote object. It does not perform or claim a production restore, test real customer records, test disaster recovery of the Cloudflare account itself, or prove that a historical migration snapshot is current.

The 10 October remote rehearsal passed five groups, including restore and undo, against 42 actual application tables. Restored record hashes matched the original exactly, with zero foreign-key errors. The synthetic namespace, temporary Worker and operator secret were removed. Fourteen focused domain/deployment/recovery safeguards also passed. New namespaces can initially return “no history”; the runner waits for native history using bounded metadata-only retries and does not repeatedly reseed customer-like data or touch production.
